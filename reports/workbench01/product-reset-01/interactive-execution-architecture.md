# Interactive execution architecture

New API boundary: `/api/workbench/interactive/**`, contract `allocationlab-interactive-spec-3.0.0`. Existing V1, spec 2.0 and spec 2.1 routes, identities, workers and evidence remain unchanged. No old run is migrated, overwritten or relabelled as interactive. The new normalized identity also records Node and V8 versions; runtime throughput/capacity is excluded. The new history deliberately lists the new interactive contract only; prior certification records remain accessible through their unchanged legacy contracts.

Express registers the new router before the older strict Workbench query middleware. All routes inherit the existing fail-closed preview-token gate and 16 KiB JSON body limit. A fixed bundled child process (`workbench-interactive-worker.mjs`) preserves the responsive API event loop. No shell, eval, user executable or path exists. Concurrency remains one through the original filesystem execution lease. Timeout, log and output bounds remain server controlled. Child memory is capped at 768 MiB. Shutdown terminates the child; timeout kills it rather than continuing uncontrolled work.

The child reuses one verified empirical dataset and bounded caches: at most 1,024 prediction entries / 16 MiB; 1,024 log-regime entries / 8 MiB; 1,024 losslessly compressed candidate/OOS books / 96 MiB; 32 risk-metric entries / 8 MiB. Books are serialized losslessly with JSON/DEFLATE level 1 and restored in full, including every actual ledger field. Compression bytes never enter financial hashes. The 24-month-window profile exposed cache eviction before this change; see performance-profile.json. Keys bind data snapshot, financial source identity, candidate definition, actual calendar, initial book, costs and cash convention. Regime caching is valid only because the active certified current-regime fit is stateless; there is no inferred learned estimator. OOS/selection cost assumptions stay distinct. Cached ledgers still pass the original turnover eligibility and tie-breaking selection at every fold. A warm rerun is a new immutable attempt, not an old result returned as a new execution.

`research/workbench/interactive-ledger.ts` is a mechanical snapshot of the original close-fill routine and its existing display helpers. Only the supplied signal calendar and memoized display-regime lookup differ. A source-equivalence test protects every financial operation. Candidate enumeration is the identical certified grid algorithm separated from its old month-start campaign validator. This is required because candidate IDs have no dependency on campaign date validation. No candidate, score, cost, regime, constraint or matched-beta formula is changed.

There are five training candidate evaluations plus one selected OOS book per fold. Unlike a full multi-scenario campaign, interactive execution computes only the explicitly requested selection-cost books and selected OOS-cost book; irrelevant cross-scenario jobs and artifact hashing are omitted. Every candidate and every fold remains evaluated. Preparation, controls, attribution and finalization add four work units.

The existing immutable store retains normalized spec, attempt states and one complete compact result. It does not materialize hundreds of per-candidate fit/prediction/job files on each exploratory click. Large-payload capacity counts two compact financial records (normalized specification and result); lease/state metadata is separate. Per-attempt output is bounded, including the final result envelope. Active progress is in memory and frozen into the final successful result. No durability claim is made. Failure evidence stays private and immutable. The unchanged store protects repository overlap and symlink boundaries.

Acceptance explicitly invokes `interactive-reference.ts` with every cache disabled, materializing complete actual candidate/OOS ledgers for reconciliation. This test/owner reference is not a public certification endpoint or a claim that an interactive result is certified. A future Certify action may materialize that evidence under a separately reviewed contract. The unmodified prior certification engines remain runnable.

Extended jobs: admission stores a validated immutable spec, then a separate bounded background worker executes larger campaigns and publishes complete immutable artifacts to external object storage. The interactive API returns a job handle and authenticates polling/retrieval. Reuse the same financial request and calendar implementation, separate operational attempt identity, explicit cancellation/recovery and checksums. A durable queue, external store and certify endpoint are FUTURE_NOT_IMPLEMENTED in this phase. No capacity default is increased.
