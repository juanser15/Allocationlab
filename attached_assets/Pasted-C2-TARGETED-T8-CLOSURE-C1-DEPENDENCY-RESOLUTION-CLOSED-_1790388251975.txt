C2 — TARGETED T8 CLOSURE: C1 DEPENDENCY RESOLUTION

CLOSED-SCOPE CORRECTION

C2 T1–T7 already pass in the reported implementation.

The only blocker is T8:
the UI rejects a valid two-alpha C2 experiment when one selected alpha
does not already have a successful compatible C1 exclusion child.

Fix ONLY this dependency/orchestration issue.

Do not change:
- C2 statistics;
- regime methodology;
- B1/B2/B3 financial logic;
- C1 comparison mathematics;
- rolling-window definitions;
- correlation calculations;
- descriptive flags;
- optimization;
- factor definitions;
- navigation architecture.

Do not begin C3.

--------------------------------------------------
1. PRINCIPLE
--------------------------------------------------

A PM must not be required to manually pre-create every C1 experiment
before running C2 diagnostics.

When C2 requires incremental-contribution evidence for selected alpha k,
it must resolve the required C1 dependency.

For each selected alpha:

A. REUSE

Reuse an existing successful C1 full-versus-without-alpha comparison
ONLY if its complete frozen specification exactly matches the C2 request.

B. CREATE

If no exact compatible C1 result exists, C2 may create the missing
C1 comparison through the existing C1 engine.

Do not approximate or synthesize the result.

C. FAIL

If the required C1 comparison cannot validly execute, preserve the
exact C1/B3 dated failure.

C2 may still show diagnostics that do not depend on incremental
contribution, but the affected incremental-contribution field must be
explicitly unavailable.

Do not label the alpha bad or remove it.

--------------------------------------------------
2. EXACT C1 COMPATIBILITY
--------------------------------------------------

A C1 result is reusable only if ALL economically relevant inputs match.

At minimum compare:

- B1 preparation identity;
- B2 frozen policy identity;
- canonical alpha IDs;
- immutable dataset identity/hash;
- development start/end;
- estimation windows;
- objective;
- expected-return shrinkage;
- covariance shrinkage;
- gamma/eta where applicable;
- portfolio constraints;
- decision calendar;
- execution timing;
- transaction costs;
- slippage;
- cash yield;
- initial NAV/holdings;
- engine versions;
- regime-independent policy assumptions used by B3.

Do not reuse based only on:
- alpha name;
- dates;
- parent experiment ID;
- similar settings.

Create and persist a deterministic compatibility fingerprint.

If any required field differs:
NOT_COMPATIBLE

and do not reuse that C1 result.

--------------------------------------------------
3. DEPENDENCY PLAN BEFORE EXECUTION
--------------------------------------------------

Before RUN ALPHA DIAGNOSTICS, show a compact dependency plan.

Example:

Alpha A
C1 incremental evidence: REUSE #17

Alpha B
C1 incremental evidence: WILL CREATE

Alpha C
C1 incremental evidence: NOT REQUIRED

Show:

- selected alpha;
- dependency status;
- matching C1 ID when reused;
- number of new C1 policies required;
- estimated total child-policy count.

Do not silently launch an unbounded number of C1 comparisons.

C2 already limits selected alphas to 5.
For each selected alpha requiring incremental contribution, allow only
the exact full-versus-without-alpha comparison needed for C2.

No pair scans.
No automatic group search.
No alpha-selection search.

--------------------------------------------------
4. CREATION OF MISSING C1 DEPENDENCY
--------------------------------------------------

When a compatible C1 result is missing:

Use the existing C1 engine.

Create:

Full frozen policy
versus
Full frozen policy without selected alpha k

using the exact C2 development period and policy assumptions.

C1 must still:

- genuinely reoptimize through B2;
- backtest through B3;
- execute through A1;
- preserve all existing failure behavior;
- persist its own immutable experiment and child Validation Runs.

C2 must store the resulting C1 experiment ID as a dependency reference.

Do not copy C1 calculations into a new C2 implementation.

Do not create a second contribution engine.

--------------------------------------------------
5. BASELINE REUSE
--------------------------------------------------

If several selected alphas require C1 comparisons under the same frozen
baseline, avoid recomputing an economically identical baseline policy
unnecessarily.

However:

- reuse only an exactly identical persisted B3 baseline result;
- preserve the child references used by each C1 experiment;
- never alter historical C1 records;
- never share mutable objects.

Optimization of computation must not weaken reproducibility.

--------------------------------------------------
6. FAILURE SEMANTICS
--------------------------------------------------

Suppose:

Alpha A C1: PASS
Alpha B C1: FAIL due to infeasibility

C2 may still complete non-dependent diagnostics.

Report:

Alpha A incremental contribution: AVAILABLE

Alpha B incremental contribution:
UNAVAILABLE — C1 dependency failed
[exact dated reason]

The overall C2 experiment may be saved as:

COMPLETED_WITH_PARTIAL_EVIDENCE

only if all core C2 calculations succeeded and unavailable diagnostics
are explicitly represented.

Do not present a complete incremental-contribution table for Alpha B.

For T8, use a fixture where both required C1 dependencies are feasible
and successful.

--------------------------------------------------
7. IMMUTABILITY
--------------------------------------------------

The C2 experiment manifest must freeze:

- dependency plan;
- reused C1 IDs;
- newly created C1 IDs;
- each dependency fingerprint;
- all child C1/B3 Validation Run references;
- C2 inputs and outputs.

Changing working settings later must not change these references.

Replay must:

1. validate the frozen C2 inputs;
2. validate every referenced C1 dependency;
3. replay/retrieve its B3 children using existing integrity mechanisms;
4. recompute C2 diagnostics;
5. compare saved versus recomputed outputs.

Do not silently search for a newer C1 experiment during replay.

--------------------------------------------------
TARGETED ACCEPTANCE TESTS
--------------------------------------------------

R1 — Exact dependency reuse

Create an existing compatible C1 single-alpha exclusion.

Run C2 requesting that alpha.

PASS only if:
- the exact C1 ID is reused;
- no duplicate C1 experiment is created;
- resulting C2 incremental numbers match C1 within 1e-8.

R2 — Missing dependency creation

Select two valid alphas:

Alpha A has a compatible C1 result.
Alpha B does not.

Run C2.

PASS only if:
- Alpha A reuses its C1 result;
- Alpha B automatically creates exactly the required C1 comparison;
- both incremental diagnostics become available;
- the new C1 result independently passes its existing integrity/replay.

R3 — Incompatible C1 is not reused

Create an older C1 result with one changed economically relevant input,
for example different costs or date window.

PASS only if:
- C2 identifies it as incompatible;
- it does not reuse it;
- a new correct dependency is created or explicit failure is returned.

R4 — Dependency failure integrity

Create a selected alpha whose required exclusion is infeasible.

PASS only if:
- C1 preserves its explicit failure;
- C2 does not fabricate incremental values;
- other independent C2 diagnostics remain viewable;
- the saved experiment records the failed dependency.

R5 — REAL UI T8

Through the actual browser UI:

1. Select at least two alphas.
2. Ensure one has an existing compatible C1 comparison.
3. Ensure the second does NOT.
4. Include:
   - multiple regimes;
   - rolling diagnostics;
   - incremental contribution.
5. Review the dependency plan.
6. Click RUN ALPHA DIAGNOSTICS.
7. Confirm C2 creates/reuses dependencies as declared.
8. Save experiment.
9. Change working settings.
10. Reload in a fresh client.
11. Retrieve the original C2 experiment.
12. Click Replay.

PASS only if:

- experiment was persisted;
- both alpha dependencies are present and immutable;
- newly generated C1 reference remains identical;
- replay returns PASS;
- no unexpected differing fields;
- maximum numeric difference <= 1e-8;
- successful replay is visible in UI.
